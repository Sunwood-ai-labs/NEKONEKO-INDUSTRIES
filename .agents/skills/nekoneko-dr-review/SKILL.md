# ネコネコインダストリーのDRレビュー

このスキルは、ネコネコインダストリー内で使うDR定義version 2に基づき、家庭試作のデータ審査を行います。共通規格の段階番号ではありません。DRは設計の妥当性を審査する段階を指し、試験を実行する呼称ではありません。記録には必ず`dr_definition_version: 2`を入れます。

| 段階 | v2の名称 |
| --- | --- |
| DR0 | 要求と検証計画 |
| DR1 | 形状設計審査 |
| DR2 | 解析・シミュレーション審査 |
| DR3 | 造形データ審査 |
| DR4 | 総合判断 |

## 対象と証拠をそろえる

1. リポジトリ直下の`AGENTS.md`と、作業対象の設計版・派生を確認します。対象年齢、用途、要求、既知の不具合を既存の記録と照合します。
2. レビュー対象とDR段階を決めます。レビュー依頼を印刷、外注、子どもの試用の許可へ広げません。
3. 確認前のデータ、確認後のデータ、根拠資料を分けて保存し、相対パスとSHA-256で結びます。変更しない入力も所在とハッシュを記録します。以前の記録を上書きしません。設計を修正するときは、[設計変更の記録ルール](../../../docs/design-change-records.md)に従い、リビジョン単位のフォルダに実データと検証結果を保存し、各版のREADMEに発端・変更理由・前版からの差分を残します。
4. [段階別の審査方法](references/stages.md)と[レビュー記録ひな形](assets/review-record.md)を使います。実施状態、判定、証拠の種類を別々に記録します。

## 断面を使う審査

断面図の出力・一覧化だけを断面DRの完了にしません。[断面レビュー手順](references/section-review.md)に従い、DR0で確認部位を計画し、DR1で実CADの形状の目的・肉厚・接続・不要な段差や突起を判断します。解析を行うDR2では断面と荷重経路・実際の積層構成を照合し、DR3では実G-codeの層断面・材料・支持接触・取り出し経路を確認します。DR4で未解決の断面所見を照合します。

各所見には位置、要求・機能、根拠、判断、処置、修正後の再確認を残します。主要部位の見落とし、機能不明の形状、必要な接続・肉厚の未確認を、図の枚数や閉じたソリッド、警告なしで合格に置き換えません。CAD改修後は、影響する断面と解析・造形経路を再審査します。

旧版の記録はDR定義version 1として保持します。v1ではDR2が造形工程、DR3が現物・設備試験でした。旧記録の段階番号や内容を上書き・付け替えません。v2の該当欄へ移すのは、対象と根拠を確認できた実証拠だけです。未実施を実施済みにしません。

## 試験とデータ審査を分ける

家庭でできない破壊、引張、噛み付き、子どもによる試用を宿題にしません。設備を要する検証は別の「実物による検証」欄に、今回の範囲外、未実施、結果なしとして記録します。必要な検証を非該当や合格に変えません。未実施の検証だけを理由に、それと独立したデータ審査を止めません。対象年齢への安全性を証明できない場合、使用可や安全認証へ読み替えません。

データ審査完了、試作データの準備、実行の承認、子どもへの使用判断は別々に記録します。このレビューは印刷、外注、子どもへの試用を承認しません。

小部品円筒（内径 1.25 in / 31.75 mm 相当）の確認も同様に分離します。CAD 上の寸法・凸包内接球スクリーニングや破断候補の抽出は **DR1**（必要に応じ **DR2** で破断解析）で実施し、**DR4** では証拠と後続試験ルートの照合のみを行います。現物の小部品円筒試験は別枠の「実物による検証」で管理し、DR4 のデータ審査通過条件には含めません。

PLAモデルに支持経路がある場合は、Support for PLAを接触界面へ明示指定し、`python quality/support-removal-preflight.py <最終スライス3MF>`を実行します。`--help`で最終引数を確認してください。材料を装着しただけでは指定済みと扱いません。プロジェクト内の材料番号と実機AMSの物理スロット番号を分け、送信直前に実際の対応を確認します。A2を固定の割当とせず、本体用PLAと専用サポート材を逆にしません。サポート経路がある設計は、現在の寸法と接触形状を代表する小さな検証片で除去できることを確認してから本体へ進みます。この条件は免除しません。支持材の移動が0なら、取り外す対象がない理由を記録します。

強度などの重い解析はKaggleでの実行を基本とします。ローカルは編集、実行の調整、結果の検査に使います。実行環境を自動でローカルへ切り替えません。

## 段階の通過条件

必須確認の「未確認・未実施・証拠不足」は、判定を保留し、該当段階を不通過にします。「条件付き」「範囲内適合」、記録の完成、個別ファイル検査の成功を、段階通過や総合合格に使いません。後続の個別検査は続けられますが、前段階が不通過なら後続段階も通過させません。

新しい記録は`gate_policy_version: 1`とし、各段階に`required_checks`と`gate_passed`、全体に`overall_gate_passed`と`child_use_approved`を記録します。必須確認にはID、判定条件、実施結果、証拠パスとSHA-256を対応づけます。必須項目の未解決を、家庭で試験できないことを理由に任意項目へ変えません。

提出前に`python tools/verify_snapshot.py --dr-gate-status <status.json>`を実行します。終了コード2は不通過、1は記録の不整合、0は記録上の段階通過です。この検査で子どもの使用を承認できません。報告の冒頭に総合の通過／不通過を明記し、`PASS_FILE_ONLY`は個別ファイル検査の結果として別に示します。

## 記録と判定

- 実施状態は「未実施／一部実施／実施済み／非該当」、判定は「未判定／範囲内適合／条件付き／不適合／保留」とします。非該当には理由を付けます。
- 証拠の種類は「人間の報告／エージェントの検査／機械記録」とします。読んだだけの資料を実行検査の証拠にしません。
- 形状値、解析結果、造形経路の観察値と、安全性・要求への判定を分けます。基準や出典のない値から合格を作りません。
- 星取表はDR0〜DR4の各行に「実物検証」「子ども使用」「印刷」の列を設けます。○はその列の確認範囲で証拠を確認した印に限り、安全、使用許可、印刷許可を意味しません。

既知の不具合を未確認や合格へ戻しません。旧個体の結果を改修版へ移しません。CADや材料、姿勢、工程が変わったら、影響を受ける判定を再確認待ちにします。
